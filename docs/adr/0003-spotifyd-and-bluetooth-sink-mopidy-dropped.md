# spotifyd for Spotify, Bluetooth sink for radio — Mopidy dropped

The playback architecture is simplified to two sources: **Spotify** via **spotifyd** (MPRIS2 + custom D-Bus controls) and **radio** via **Bluetooth sink** (the phone plays a radio app, the Pi renders the audio stream as a Bluetooth A2DP sink). **Mopidy is removed entirely** — it is no longer a runtime dependency, and `mopidy-spotify`, `mopidy-mpris`, and the internet-radio extensions are gone.

This supersedes [ADR 0001](./0001-mpris2-mopidy-as-playback-abstraction.md), which chose MPRIS2-via-Mopidy as a single abstraction covering both Spotify and internet radio. The reasoning in 0001 — that spotifyd "exposes no rich metadata/queue over D-Bus, forcing the UI to special-case every source" — is no longer accurate: spotifyd now implements full MPRIS2 (`org.mpris.MediaPlayer2.Player`: `Play`, `Pause`, `Next`, `Previous`, `Stop`, `OpenUri`, `Seek`, `SetPosition`; `Metadata` with `xesam:title`/`xesam:artist`/`xesam:album`/`mpris:artUrl`/`mpris:length`; `PlaybackStatus`; `Position`; `Volume`; `Seeked` and `PropertiesChanged` signals).

## What changed

- **Spotify** is now served by **spotifyd**, which exposes a custom D-Bus interface `rs.spotifyd.Controls` (always available once connected to Spotify: `TransferPlayback`, `VolumeUp`, `VolumeDown`) and full MPRIS2 (available only when spotifyd is the active playback device: well-known name `org.mpris.MediaPlayer2.spotifyd.instance$PID`).
- **Internet radio** is no longer a first-class source. Radio is played from a phone via a radio app (TuneIn, etc.), with the Pi acting as a Bluetooth A2DP sink. The Now-Playing view for this case is the existing Sink Mode variant — no scrubber, no transport, "Controlled by <Paired Device>".
- **Mopidy is gone.** No `mopidy`, `mopidy-spotify`, `mopidy-mpris`, or `mopidy-tunein`/`mopidy-internetarchive` extensions. No Mopidy config, no Mopidy D-Bus service. The system repo no longer configures Mopidy.

## Considered Options

- **spotifyd for Spotify + Bluetooth sink for radio** (chosen) — two clear sources, each with a distinct D-Bus shape: spotifyd gives MPRIS2 for Spotify, Bluetooth sink gives PipeWire-routed audio for radio. Removes an entire daemon (Mopidy) and its extension ecosystem. Spotify Connect is free — other devices can push playback to the Pi.
- **Mopidy for both (ADR 0001)** — rejected. `mopidy-spotify` has been flaky with Spotify's auth changes; Mopidy is a heavier dependency than spotifyd for a single-source use case; and the original justification (spotifyd lacks MPRIS2) is obsolete.
- **spotifyd + Mopidy for radio (keep Mopidy for radio only)** — rejected. Radio is a rare use case for this device; keeping Mopidy solely for radio is not worth the operational cost. Bluetooth sink covers it.
- **spotifyd + Mopidy both doing Spotify** — rejected. Two ways to play the same source is confusing and they'd fight over the audio sink.

## Consequences

- **"Source" is a simple toggle, not a full view.** With only two sources, a dedicated Source Selection view is not warranted. The source toggle is the existing Source badge in the Status Bar — tapping it switches between Spotify and Bluetooth. Tapping to Bluetooth calls `switchToBluetooth()`: pauses spotifyd, then enters `BluetoothWaiting` (no device connected) or `BluetoothActive` (device already connected). Tapping to Spotify calls `switchToSpotify()`: pauses Bluetooth (if active), then queries the bus for the appropriate Spotify state. The badge shows "…" while switching and resets when `playbackState` changes.
- **`PlaybackController` exposes a single `playbackState` enum** with five values: `SpotifyUnavailable` (spotifyd not running — error state), `SpotifyReady` (Controls present, MPRIS2 absent — show "Transfer Playback" prompt), `SpotifyActive` (MPRIS2 present — normal Now-Playing), `BluetoothWaiting` (user switched to Bluetooth but no A2DP source connected — show "Discoverable — connect your phone"), `BluetoothActive` (A2DP source connected — show "Controlled by <Paired Device>"). QML switches on this one value rather than combining booleans. `isSpotifyPlaying` is a sub-property of the `SpotifyActive` state. `isBluetoothActive` is kept as a convenience (`playbackState === BluetoothActive`). Bluetooth mode is only entered by explicit user action, never by a BT connection event alone.
- **The toggle action pauses the other source.** When switching to Bluetooth, `switchToBluetooth()` pauses spotifyd first. When switching to Spotify, `switchToSpotify()` pauses/disconnects Bluetooth first. This is distinct from the automatic behavior: a phone connecting via BT while in a Spotify state does NOT pause spotifyd or switch the app to Bluetooth mode — only the explicit toggle action does.
- **No auto-switch on BT connect.** When a phone connects via Bluetooth A2DP while the app is in a Spotify state, the app does **not** automatically pause spotifyd or switch to Bluetooth mode. A phone connecting simply routes audio through PipeWire in the background — the app stays in whatever playback state it's in. Only the explicit toggle action pauses the other source.
- **Bluetooth mode is opt-in.** A Bluetooth A2DP source connecting does NOT automatically change `playbackState`. Bluetooth mode is only entered when the user taps the Source toggle. If a phone is already connected, `switchToBluetooth()` enters `BluetoothActive` immediately. If no phone is connected, it enters `BluetoothWaiting`. If a phone disconnects while the app is in a Spotify state, nothing happens. If a phone disconnects while in `BluetoothActive`, the app queries the bus: `SpotifyActive` if MPRIS2 is available, `SpotifyReady` if only Controls is present, `SpotifyUnavailable` if neither.
- **MPRIS2 is only available when spotifyd is the active device.** The Now-Playing view for Spotify must handle the "not yet the active device" state: show a prompt ("Select this device in Spotify, or tap to transfer") with a button that calls `TransferPlayback`. Only after the MPRIS2 name appears does the full Now-Playing UI activate.
- **The `$PID` suffix in spotifyd's well-known name changes on restart.** `PlaybackController` must discover the name dynamically (list names and match `org.mpris.MediaPlayer2.spotifyd.*`) or use a `QDBusServiceWatcher` with a name match, not hardcode it.
- **Radio is not scrubbable and has no metadata.** In Bluetooth mode (radio via Bluetooth), the Pi only knows the paired device name. There is no track title, no station name, no art — just "Controlled by <Paired Device>".
- **Two audio producers, one sink — the toggle coordinates, automatic events don't.** spotifyd and a Bluetooth A2DP source both output to PipeWire. The explicit toggle action pauses the other source before switching. But a phone connecting via BT does not trigger a pause or state change — only the user tapping the toggle does.
- **spotifyd D-Bus session bus sharing.** spotifyd exposes both its custom `rs.spotifyd.Controls` interface and MPRIS2 on the **session bus** by default. The system repo runs spotifyd as a **systemd user service** (`systemctl --user`), not a system service. This ensures spotifyd starts when the kiosk user's session begins (cage creates the logind session → `systemd --user` starts → spotifyd starts) and automatically shares the same D-Bus session bus as the cage-launched app. No `DBUS_SESSION_BUS_ADDRESS` injection, no UID guessing at build time, no ordering dependencies on the cage service. The app uses `QDBusConnection::sessionBus()` and finds spotifyd's interfaces without any bus address configuration.
- **Adding a future Mopidy-backed source (e.g. podcasts) is no longer free.** ADR 0001's "just add a Mopidy extension" consequence no longer applies. A future source would require re-introducing Mopidy or finding another MPRIS2-capable player.
- **`ArtCache` still relevant.** spotifyd's `mpris:artUrl` may be a remote `https://` URL (Spotify CDN) — the cache is still useful.
